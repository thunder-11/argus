## 1. Executive Summary

The platform shall accept victim-reported suspect cryptocurrency wallets, automatically initiate authorized investigations, retrieve real blockchain evidence, trace outgoing movements, identify supported exchange/VASP destinations, classify suspicious behavior, correlate victims, and produce explainable investigation reports.

This update preserves valid requirements from the original attached PRD and the preceding backend/integration specification. It adds a fully specified transaction graph filter anchored to the exact victim report timestamp and replaces all prior ML preservation/extension requirements with a completely new, independently developed ML system.

The new ML subsystem shall not import, copy, extend, distill, warm-start from, call, or otherwise depend on existing backend ML code, trained models, feature definitions, preprocessing, labels generated by that ML, scores, explainers, training pipelines, experiment results, or model artifacts. Compatibility with a legacy API is a transport concern only and shall not introduce an old ML dependency.

Each prediction shall identify its target, risk score, calibrated probability/confidence semantics, contributing features, evidence, temporal scope, model version, calibration version, and analyst review state. ML provides decision support, not definitive proof of fraud.

Post-report graph filtering shall select transactions with blockchain event timestamps strictly later than the selected victim report timestamp by default. Pre-report evidence remains retained and independently accessible as context. Filtering shall neither delete evidence nor leak later activity into an earlier prediction.

## 2. Problem / Objectives

Investigators receive suspect wallets that may be collection, burner, intermediary, or exchange deposit addresses. They need to identify the nearest evidence-supported receiving VASP, observe movements after the victim reports, and distinguish actionable facts from uncertain inferences.

Objectives:

- O-01: Validate manual and complaint-extracted wallets and automatically queue investigations.
- O-02: Retrieve complete-within-scope real native/token history on BTC, ETH, TRON, BSC, and Polygon.
- O-03: Produce directed wallet graphs and coherent five/six-hop paths when the evidence supports them.
- O-04: Identify deposit/off-ramp points with attribution evidence and interaction risk.
- O-05: Detect suspicious wallet/transaction behavior using independently built ML and explicit deterministic rules.
- O-06: Separate pre-report evidence, at-report activity, and post-report activity.
- O-07: Provide calibrated decision support without hindsight or graph leakage.
- O-08: Correlate distinct victim complaints and explain shared fund trails.
- O-09: Provide timely partner deposit checks and durable alerts.
- O-10: Generate authentic-looking, factually qualified LEA reports and reviewable legal drafts.
- O-11: Integrate current frontend surfaces entirely through contracts.
- O-12: Provide reproducible, auditable, secure and operable services.

Measure acceptance latency, first-result/first-attribution latency, provider lag, successful/partial runs, attribution precision, review precision/recall, calibration, abstention, alert delivery, evidence integrity, and performance by supported cohort. No perfect-accuracy or guaranteed-recovery claim is permitted.

Use a modular FastAPI application with separately scalable workers. Preserve suitable non-ML services and the prior PostgreSQL/Neo4j/Redis/Celery architecture. The local SQLite-style prototype may remain an isolated development fixture store; authoritative production investigation storage uses PostgreSQL.

| Layer | Responsibilities and separation |
|---|---|
| API/routes | HTTP methods, auth dependencies, query/schema validation, versioning |
| Controllers | Request-to-use-case mapping; no provider parsing or ML computation |
| Services | Intake, case, tracing, attribution, reporting and orchestration |
| Provider adapters | Chain-aware external requests, pagination, errors and capabilities |
| Blockchain data pipeline | Immutable observations, normalization, finality, historical snapshots |
| Deterministic analytics | Specified pattern rules, allocation hypotheses and sourced attribution |
| New ML boundary | Entirely independent data transforms, features, training, registry, inference, explainability and monitoring |
| Database/models/repositories | Transactions, indexes, point-in-time queries and persistence |
| Jobs/queues | Durable trace, NLP, prediction, document, alert and refresh jobs |
| Integrations | Government intake, VASP checks, protocol resolution and dispatch |
| Authentication/security | Users, partner clients, sessions and authorization |
| Configuration | Typed settings, thresholds and environment-only secrets |
| Utilities | Independently reviewed amount/time/address/hash helpers; no old ML-derived helpers |

PostgreSQL is authoritative for cases, report-time revisions, observations, runs, predictions, labels and evidence manifests. Neo4j is a rebuildable, revisioned graph projection. Redis is a cache/registry/coordination store, not the sole evidence store. Objects store raw provider responses, snapshots, artifacts and PDFs with access control and hashes.

A transactional outbox coordinates committed records and worker/events. The graph and ML use explicit snapshot references. Graph queries are read-only: fetching an empty graph shall not trigger hidden tracing.

The new ML boundary may consume the platform's documented normalized evidence API or independently verified raw non-ML observations. It shall not read or execute an existing ML module, old feature table, old prediction cache or old model-generated label. Freshly re-derived features are mandatory.

Provider routes/plans must be revalidated before implementation; old Etherscan V1 or deprecated per-instance Blockscout routes shall not be assumed operational.

### 7.2 Pipeline requirements

Validate network → fetch bounded pages/checkpoints → preserve raw observation → normalize → verify successful movement/finality → persist exact transfers → produce temporal snapshot → expand graph → derive independent features/analytics → predict → review/alert/report.

Each observation stores provider, network, retrieval time, provider publication time if known, first platform availability, block hash/height, page/cursor, parser version, raw-object hash and coverage. Missing provider publication time remains null.

BTC inputs and outputs remain separate; do not allocate every output to the first sender. Multiple token logs/internal calls in one hash remain distinct. Failed calls are not successful movement. Pending observations have their own status and cannot acquire invented block timestamps. Token identity is network plus contract; symbol alone is insufficient.

### 7.3 Tracing and attribution

Default four hops, allowed one through six. Apply incident chronology and receipt-relative traversal order. Prioritize amount at least 10% of compatible reported loss OR greater than USD 50 with sourced valuation. If amount/valuation is missing, use a disclosed bounded alternative and mark the threshold unevaluable. Track pruned branches.

Check root labels; stop each branch at the first supported receiving VASP, retaining a corroborating sweep. Rank nearest by supported hop count, then evidence quality and relevant value; preserve alternatives. Address clustering and fungible allocation are hypotheses, not ownership proof.

Keep native/token flows and explicit swaps distinct. Do not sum repeated transit edges as victim loss or recovered amount. Missing providers produce partial/unavailable coverage rather than false zero activity.

### 7.4 Cross-chain and privacy boundaries

Maintain sourced protocol/version registry for Stargate/LayerZero, Portal/Wormhole, Polygon PoS Bridge, THORChain, Hop, relevant Binance mechanisms, historical Multichain contracts, and named swap services where evidence exists. A protocol message/nonce plus verified source/destination execution supports continuity; time/amount similarity alone creates a candidate.

The original 45-minute and 95–100% amount window remains a configurable candidate heuristic. Failed, ambiguous, pending, unresolved and unsupported links remain explicit. LayerZero transaction/message APIs are one potential resolver source: [official Scan API](https://docs.layerzero.network/v2/tools/layerzeroscan/api).

Provide the checklist examples Wallet → Wallet → Mixer → Wallet → Binance/VASP and Ethereum → Bridge → Polygon → Exchange only when supported by evidence or explicitly labeled fixtures. A synthetic mixer exit or cross-chain hop shall never become a confirmed live edge.

## 8. Investigation / Case Workflow

### 8.1 Intake and automatic initiation

Manual intake creates a minimal case and root. Complaint intake supports source/external reference, victim details, narrative, report receipt time, filing/incident times, loss/asset and multiple suspect wallets. Local extraction provides candidates with spans/confidence; only validated network-resolved candidates may start automatically. Missing prerequisites create `awaiting_input`, not a fabricated root or completed investigation.

A successful valid intake commits complaint, report event, wallet links, case and queued run in one transaction/outbox workflow. Return HTTP 201 with case/complaint/trace identifiers. Existing frontend follow-up POST trace uses the same idempotency key or equivalent-run key to return the existing queued/running run.

Keep separate complaints and report events even when merged into a case. Imported source timestamps are validated and retain source confidence. Identical retries replay; conflicting duplicates return 409.

### 8.2 Case and run states

Canonical case lifecycle: `new`, `investigating`, `escalated_to_vasp`, `frozen`, `closed`. Preserve transitions new→investigating/closed; investigating→escalated_to_vasp/frozen/closed; escalated_to_vasp→frozen/closed/investigating; frozen→closed/investigating; closed→investigating. Local NEW/UNDER_INVESTIGATION/ATTRIBUTED values receive documented compatibility mapping; attribution is a separate state.

Analysis: `awaiting_input`, `queued`, `running`, `cancel_requested`, `cancelled`, `completed`, `partial`, `failed`. ML and report jobs have independent status. A trace may complete without a VASP.

Escalated/frozen states require recorded external action/confirmation. Notes, assignment, revision conflicts, reasons and reopening remain auditable.

### 8.3 Correlation and deposit workflows

Two distinct complaints yield relatedness. Three distinct victims/complaints sharing a relevant suspect/intermediary wallet yield a syndicate candidate. Exclude duplicated intake and common public services as sufficient evidence. Return authorized linked cases and shared trail.

The exact checklist wording “High-Confidence Fraud” / “3 Victims → Same Wallet → Common Fund Trail → HIGH CONFIDENCE FRAUD” is a demonstration/review presentation requirement. Its live representation must state “high-confidence shared-wallet correlation; suspected fraud, analyst review required”; a categorical adjudicated label requires human confirmation. Three reports alone do not prove fraud or calibrate a probability.

VASP deposit checks use prepared, fresh risk information and optionally fast new-model inference on available features. A partner-controlled credit gate can await a durable BLOCK/REVIEW alert decision before crediting. Without such a hook, label the result monitoring/advisory and do not claim funds were blocked or alerts preceded credit.

### 8.4 Reports and legal drafts

The existing Generate Report action creates an asynchronous PDF job. Include every Section 5 F-13 field, selected report cutoff/revision, pre/post evidence separation, graph legend/snapshot, model/calibration versions, explanations/review, providers, limitations, full references and hashes. Format for LEA use without impersonating official approval.

Preserve Section 94 BNSS / historical Section 91 CrPC document-request templates and separately reviewed freezing/seizure authority. Preserve BSA Section 63 / historical IEA Section 65B certificate drafting with human completion/signature. No automatic court-certified flag. Cite applicable reviewed template sources: [BNSS](https://www.indiacode.nic.in/handle/123456789/20099?view_type=browse), [BSA](https://www.indiacode.nic.in/bitstream/123456789/20063/1/a2023-47.pdf).

Hash canonical evidence manifest; embed its digest in the PDF; hash final PDF bytes separately. Store immutable versions. A corrected cutoff generates new reports and supersession metadata without changing old bytes.

## 9. Transaction Graph / Post-Report Filtering

### 9.1 Timestamp definition

`victim_reported_at` (T0) is the instant the victim's report was first received by the selected reporting channel for the selected complaint, supported by source receipt metadata or an explicitly recorded investigator assertion. It is NOT incident time, case creation time, ingestion time, trace start, transaction retrieval time or forensic report generation time.

Report event stores `id`, `complaint_id`, `reported_at_utc`, original ISO timestamp/offset, optional IANA timezone, source/channel, receipt reference, source precision, verification status, `recorded_at`, author and revision. Corrections are append-only revisions with reasons.

For direct intake the server's authoritative receipt instant is recorded. For externally received reports use validated source receipt time. A victim-stated earlier reporting time is an assertion pending verification. Never silently replace a missing exact report time with `created_at` or `incident_timestamp`.

### 9.2 Timezone and precision

Require ISO-8601 with Z or explicit offset. Convert once to UTC; retain original representation. An IANA zone is display/source context and shall agree with the supplied offset for that date. Reject unresolvable offset-less, ambiguous/nonexistent local times. Display UTC and Asia/Kolkata where requested; never use browser timezone for comparison.

Persist supported microsecond precision; reject unsupported precision rather than silently round across the boundary. Validate future source report times against a configured five-minute clock-skew allowance; larger discrepancy requires correction/review.

Blockchain timestamps often have only second/block precision and do not establish exact wall-clock transaction execution order. Compare the reported ledger event timestamp exactly at its supplied precision, record `event_time_basis` and `timestamp_precision`, and disclose this limitation. Do not invent subsecond times or cross-chain causal ordering. Same-block ordering may order a path but shall not move an equal-timestamp event across T0.

### 9.3 Boundary rules

| Partition | Rule |
|---|---|
| Pre-report evidence | event_time < T0 |
| At-report boundary | event_time = T0 |
| Strict post-report activity (default) | event_time > T0 |
| Inclusive post-report view (explicit option) | event_time >= T0 |
| Unknown-time evidence | event_time missing/unusable |

Default `boundary=exclusive` implements the user's “after” requirement. Inclusive behavior requires `boundary=inclusive`, is visible in metadata/export, and does not relabel boundary records as strictly later.

Default end cutoff is the immutable run's event cutoff T1, with event_time <= T1. A client-supplied `to` may narrow but not exceed the snapshot. From/to are UTC. No report cutoff: `post_report` returns 422 REPORT_TIMESTAMP_REQUIRED, while an all-history context investigation may continue.

### 9.4 Multiple complaints and corrections

A case may have different victim report timestamps. Post-report requests must identify `report_event_id` and revision. Auto-select only for one eligible primary report event and return the selection. Multiple eligible events without an explicit designated primary produce 422 REPORT_REFERENCE_REQUIRED. Never choose the earliest/latest silently.

After correction, old runs/predictions retain their cutoff revision. New runs reference the new revision. Asking an old run to use a new revision returns 409 SNAPSHOT_CUTOFF_MISMATCH; create a new snapshot/run for the corrected interpretation.

### 9.5 Graph behavior

The default filtered graph includes selected post-report edges and their incident wallet nodes, plus explicitly marked root/anchor nodes where needed. Remove other isolated nodes unless requested. Graph node IDs are network-qualified; the actual address is a separate field.

Pre-report and at-report transactions remain in storage. With `include_context=true`, return them in separate `context_nodes` / `context_edges` collections with `context_only=true` and temporal partition. They are excluded from selected counts, amounts, post-report alerts, animation steps, and post-report-only feature aggregates. The existing graph may display them distinctly using metadata; no new UI is specified.

A path that crosses T0 may become disconnected when context is hidden. Return path gaps/anchor references; never insert fictitious edges to maintain visual continuity. Retain original full-path hop count and selected transfer count as distinct fields.

For a cross-chain transfer with a pre-report lock and post-report release, select only the post-report on-chain event as activity. The source event may be context; the cross-chain relationship remains a derived link with both evidence references. Never count both legs as newly moved post-report funds. Mixer boundaries remain unresolved unless evidence supports continuation.

Clusters computed for an earlier snapshot must not contain later-discovered structure. Response includes cluster snapshot/version and whether membership is context-derived.

### 9.6 Query and API semantics

`GET /api/v1/cases/{id}/graph` accepts `trace_id`, `temporal_view=all|pre_report|post_report`, `report_event_id`, `report_revision`, `boundary=exclusive|inclusive`, `include_context`, `to`, chain/asset/entity filters and graph bounds.

Existing clients omitting `temporal_view` retain `all` compatibility. The post-report workflow explicitly requests `post_report`; once requested, default boundary is exclusive and default context is false. The API must echo effective filters. A filter changes a projection, not the run's evidence or prediction.

The same temporal parameters apply to transaction lists, paths, aggregates and report generation. Context has its own pagination/truncation metadata. Cursors bind case, run, revision, report cutoff, filters, sort order and authorization scope; mixing filters invalidates a cursor.

Graph metadata: report reference/revision, effective T0/T1, boundary, timestamp basis, selected/context/boundary/unknown counts, coverage, pruning, graph revision and prediction references with their own temporal scope. Unknown-time records are excluded from strict filters and retained in a separately counted unresolved collection.

### 9.7 Boundary examples and acceptance

For T0 = 2026-09-12T10:00:00.500000Z: .499999Z is pre-report; .500000Z is boundary; .500001Z is strictly post-report. The equivalent +05:30 timestamp yields identical classification. A timestamp at whole second 10:00:00Z compares as that ledger instant, with one-second precision disclosed; no claim is made about intra-second execution.

Tests must cover equality, offset equivalence, precision rejection, DST ambiguity, missing T0, unknown transaction time, late arrival, report correction, multi-complaint selection, independent context, cross-chain boundary, pagination, cache isolation, reorg and export reproducibility. IDs TG-01 through TG-14 in Section 22 define release gates.

## 10. Fraud / Risk Analytics

Keep four distinct outputs: deterministic composite risk (0–100), new ML calibrated risk (0–100 with probability), entity attribution confidence, and correlation evidence/score. Do not merge them under an unlabeled percentage.

Preserve the original independently specified six-factor composite policy: mixer +30, bridge/swap +20, at least three outgoing transfers in 60 minutes +15, repeated >80%/<20% peeling +15, sufficiently evidenced first on-chain activity within seven days +10, and linkage to two other distinct complaints +10. Cap at 100; one weight per factor. Keep a separate 30-minute rapid-dispersal finding. This policy is specified here, not imported from existing ML code.

Add explicit structuring/splitting, path depth, rapid progression toward a VASP, fan-in/fan-out and consolidation findings for the checklist. Do not silently change composite weights; any new weighted policy is separately versioned. Amount thresholds must not be presented as jurisdictional reporting rules without sourced authority.

Composite tiers: <30 low, 30–59 medium, 60–84 high, >=85 critical; unknown for unassessed evidence. Unevaluated factors are unknown, not false. Attribution tiers retain versioned initial heuristic scores 95 exact, 85 sweep, 65 qualified cluster; these are NOT calibrated ML confidence. A sweep candidate initially uses >=85% of an explicitly defined same-asset amount within six hours, with observed fees/residuals and ambiguity disclosed.

An entity's FIU registration, nationality or legal jurisdiction is not a fraud feature. A VASP receiving funds is an attribution fact; interaction risk concerns the observed route. Tether treasury, foundations, contracts and issuers must not be mislabeled as exchanges.

An explanation such as “five hops, INR 8.4 lakh in four minutes, mixer interaction, VASP deposit, three complaints” is allowed only when evidence, currency conversion and timestamps support every part; otherwise use labeled demo fixtures or omit unsupported statements.


## 11. New ML Architecture

### 11.1 M-01 — Independent development boundary

The new subsystem shall be designed, trained, validated and operated from scratch. Prohibited inputs/dependencies include existing backend ML/NLP/risk classifier implementations, model files, weights, embeddings, feature columns, scalers, imputers, training scripts, split files, inference functions, explainers, synthetic labels generated by old models, performance claims and experiment configurations.

Do not preserve an old model as a challenger or fallback. Do not train to imitate an old model. Do not rename existing modules as evidence of independence. All learned components, including calibrators and optional graph encoders, start fresh. General-purpose third-party libraries are permitted; library choice does not authorize reuse of existing project ML.

Permitted reuse is limited to authenticated non-ML APIs, case IDs, reviewed raw blockchain observations, provider adapters that do not contain ML logic, storage/queues and independently verified directory facts. Newly collected public datasets may share a public origin with older work, but must be acquired and processed independently with a new manifest; old prepared datasets/features are prohibited.

Independence evidence shall include a dependency/import audit, artifact checksums and provenance, new data/feature/training manifests, no legacy model calls in integration tests, and a clean deployment test with all old ML resources inaccessible.

### 11.2 M-02 — Problem formulation

Primary targets are separately evaluated:

| Task | Unit and input | Label/output |
|---|---|---|
| Wallet snapshot risk | Network-qualified wallet, evidence snapshot, event cutoff, knowledge cutoff | Probability that reviewed evidence supports fraud-linked suspicious activity in the declared observation window |
| Transaction/transfer risk | Unique transfer plus eligible prior/context graph and event metadata | Probability that the reviewed transfer belongs to fraud-linked suspicious activity |
| Pattern classification | Eligible route/window/transfer | Multi-label rapid movement, multi-hop, splitting/structuring, mixer, bridge, rapid exchange progression; probabilities only for trained/validated labels |
| Complaint typology | Locally processed complaint text available by the prediction cutoff | Seven required typologies plus unknown, with separately evaluated confidence |

This is classification of observed activity, not a claim that a wallet owner is criminal and not an implicit prediction of future crime. Any later forecasting target requires a separate formulation, horizon, model, validation and API version.

The supervised binary label concerns activity within the observation window. Adjudication may arrive later, initially within a 90-day maturation window; this is label maturity, not a feature window or a forecast horizon. Unresolved/censored samples remain unknown.

Case risk is initially an explicit aggregation of wallet/transfer findings (maximum reviewed eligible score plus counts, with method stated), not a calibrated case probability. Entity ownership attribution remains sourced analytics, not a replacement ML target.

### 11.3 M-03 — Temporal operating modes

| Mode | Allowed features | Meaning |
|---|---|---|
| report_baseline | event_time <= T0 AND available_at <= T0; label/directory/complaint facts also known by T0 | Reproducible as-known-at-report assessment |
| post_report | Baseline snapshot plus separately namespaced events T0 < event_time <= T1, all available_at <= K1 | Assessment updated through explicit later event and knowledge cutoffs |
| retrospective_context | Historical event_time <= cutoff with later retrieval/enrichment permitted and declared | Present-day reconstruction; cannot be called what was known at report time |

T1 is the prediction event cutoff and K1 its knowledge cutoff, normally the actual prediction snapshot time. Baseline cannot consume post-report transactions, later complaints, later exchange labels, later analyst decisions, future block confirmations, or later resolved bridge destinations.

For a new platform with no historical availability record, reconstructed pre-report data cannot establish a true report_baseline. Return insufficient_as_of_coverage or explicitly offer retrospective_context. Do not backdate available_at to event_time.

Post-report inference may use genuine baseline context, but pre and post features must remain separately namespaced and counts/aggregates auditable. It must never overwrite the baseline prediction. A post-report graph filter does not automatically convert a baseline prediction into a post-report prediction.

### 11.4 M-04 — Components and flow

Independent data collection → immutable dataset snapshots → human-reviewed label store → point-in-time feature service → split/training runner → validation/tuning → separate calibration → immutable model registry → approved inference service → evidence explainer → analyst review → monitoring and controlled retraining.

Required components: dataset catalog; label adjudication; feature registry; offline/online feature materialization; training orchestrator; experiment tracker; artifact registry; calibration registry; low-latency serving; explanation jobs; review queue; drift/performance monitor; promotion/rollback controller.

CPU-friendly baseline models are mandatory before a complex graph ensemble is considered. Training is separated from API processes. No network collection or training occurs synchronously inside model inference.

### 11.5 M-05 — Model/ensemble selection

Train fresh candidates: regularized logistic regression baseline, independently configured gradient-boosted tree candidate, and a random-forest challenger. Compare with an independently implemented specification-based deterministic rule baseline. Optional temporal graph/sequence models require enough labeled data, causal neighbor sampling, inductive evaluation and operational benefit.

Choose the simplest candidate meeting quality/calibration/latency gates. Ensemble voting/stacking is permitted only when out-of-time out-of-fold base predictions train the combiner; calibrate the final ensemble on a separate later set. No validation/test records may train base models or the combiner. Evaluate latency and explanation consistency before adding complexity.

Anomaly detection may provide an auxiliary signal from an independently trained model. Anomaly score is not a fraud probability and cannot replace validated supervised outputs. No model family or “AI” branding is mandated as evidence of quality.

## 12. ML Data / Features

### 12.1 M-06 — Data sources and collection

Collect real blockchain observations through Section 7 adapters and retain licensable raw references. Obtain reviewed outcomes from authorized investigations, verified external labels with provenance and availability dates, and independently acquired public research datasets whose task/units match the formulation. Public BTC datasets do not establish ETH/TRON performance.

For each source register owner, license/terms, permitted purpose, chains, coverage dates, collection method, identity keys, label meaning, availability semantics, quality limits, retention and deletion constraints. No paid feed, official fraud label API or dataset size is assumed available.

A concrete optional research source is the independently acquired Elliptic/Elliptic++ BTC data from its original publishers: [Elliptic dataset announcement](https://www.elliptic.co/insights/elliptic-dataset-cryptocurrency-financial-crime/) and [Elliptic++ research repository](https://github.com/git-disl/EllipticPlusPlus). Its published task/graph/labels may inform a separately labeled research evaluation after licensing review; no old project-prepared feature columns or models are reused. If raw provenance cannot reconstruct the new features/cutoffs, it does not satisfy production acceptance.

Public research data without trustworthy timestamp/label provenance is restricted to exploratory experiments; it cannot certify point-in-time production gates. Synthetic graphs are permitted for boundary, security and demo testing but excluded from real-world quality/calibration claims. Keep live/demo/research partitions and access policies distinct.

Collect longitudinal snapshots and representative reviewed negatives, including legitimate high-activity services, exchange deposits, bridges and privacy interactions to measure false positives. Log collection biases and provider gaps.

### 12.2 M-07 — Labels and adjudication

Labels: positive (reviewed support for target activity), negative (reviewed legitimate/no supporting target evidence under the defined review protocol), unknown, disputed and censored. No complaint, no exchange label or no model alert is not a negative.

Store subject/window, class/pattern, evidence, source confidence, event validity, first knowledge time, adjudication time, reviewer IDs, agreement/disagreement, maturity, revision and license. Duplicate labels merge through adjudication, not vote inflation.

Use two independent reviewers for the gold evaluation set; adjudicate disagreements. Reviewers are blinded to model score where feasible. Record inter-reviewer agreement and class-specific disagreements. Analyst operational overrides remain a feedback proposal until independently adjudicated; they do not automatically become labels.

Later confirmed evidence may supply the target label for an earlier snapshot, but cannot enter that snapshot's features. Training samples may use only labels available by that training run's label cutoff. Evaluation ground truth is frozen after the declared maturation period; report censoring and delayed-label bias.

### 12.3 M-08 — Preprocessing

Independently define normalization, deduplication, filtering and transformations. Use network-qualified addresses, exact asset IDs, event IDs and UTC. Preserve original units; create sourced converted features with quote timestamp and availability cutoff.

Handle missingness explicitly with indicators and train-only fitted imputation. No fabricated fee/block/age/zero-activity data. Reject invalid records, quarantine suspicious provider payloads and retain reasons. Robust transforms/winsorization may operate on model features using train-only parameters; raw evidence remains unchanged.

Fit scaling, imputation, category encoding, feature selection and dimensionality reduction inside training folds only. Freeze all transformations into the model package. Do not derive learned transformations or vocabulary from final test data. Prevent case-sensitive address corruption.

### 12.4 M-09 — Feature families

Every feature has a new definition, unit, scope, window, source, availability rule, missing-value behavior, aggregation, owner and version.

| Feature family | Examples and constraints |
|---|---|
| Amount/asset | Exact amount, log-transformed normalized magnitude, asset-specific transfer distribution, sourced value ratio, fee metrics only when observed |
| Velocity | Count/value in 1m/5m/30m/60m/24h/7d/30d windows, inter-arrival distribution, time from receipt to spend |
| Structure/splitting | Fan-out/fan-in, unique counterparties, split concentration/entropy, repeated small components, conservation-aware peeling ratios |
| Path | Supported hop depth, traversed time, value retention, number of intermediary wallets, time toward first observed VASP destination |
| Wallet history | First observed activity and coverage-qualified age, active intervals, recurrent counterparties |
| Graph | Directed in/out degree, bounded temporal motifs, recurrence, components/cluster evidence, causal neighborhood risk exposure |
| Protocol interactions | Supported mixer/tumbler, bridge, swap/DEX interaction count and value; source/version/availability required |
| VASP interactions | Receiving deposit/hot-wallet evidence, temporal proximity, concentration, observed sweep ratio; no assumption of guilt |
| Correlation | Distinct prior authorized complaints/victims, known-at-time shared intermediary count; exclude current target complaint/self-label leakage |
| Data quality | Coverage, provider lag, truncated neighborhoods, missing-price/fee/history indicators |
| Narrative | Newly designed local text representations for the separate typology task, excluding PII and verdict/outcome text |
| Post-report deltas | Separately named post-report counters and change from frozen baseline, using only T0 < events <= T1 |

The requested five-hop, four-minute, INR 8.4-lakh example is derived from observed transfers and sourced conversion, not a hardcoded feature outcome.

Exclude wallet strings, case IDs, victim/officer identities and investigation decisions as predictive shortcuts. Entity IDs may be used for deduplication/grouping but not memorization features. Audit geography, language, chain and exchange proxies. Registration/compliance status shall not be a fraud target proxy.

### 12.5 M-10 — Temporal/graph leakage controls

- Store event_time, available_at and revision validity separately.
- Point-in-time joins apply both event and knowledge cutoffs.
- Compute baseline graph on eligible edges only; no future neighbors, labels, degrees, clusters, shortest paths or embeddings.
- Train graph embeddings only on eligible training graph; no transductive test-graph access for the inductive benchmark.
- Group repeated wallets, related complaints, duplicates and known campaign clusters to prevent leakage across train/test.
- Exclude the target complaint and current complaint count from features that trivially define its positive label; known independent prior complaints remain separately eligible.
- Do not use later freeze, VASP response, review verdict or report text as features.
- Prevent future token metadata, prices or directory labels from entering historical features unless explicitly classified retrospective.
- Record max contributing event_time and max available_at on each feature snapshot.
- Leakage tests insert future events/labels and assert an unchanged earlier feature snapshot/prediction.
- Reorganizations and label corrections create new revisions, not backdated mutations.

## 13. Training / Validation / Evaluation

### 13.1 M-11 — Split protocol

Define a chronological train → tuning validation → calibration → final test order using distinct snapshots. Use at least three rolling-origin validation windows when data volume supports them. Freeze dates, grouping rules and class counts in the dataset manifest before training.

Apply a purge/embargo sufficient for overlapping observation and label-maturation windows; initial conservative gap is at least the maximum feature lookback or documented overlap risk, with 90-day label maturity enforced separately. No label unavailable by a training deadline may train that run.

Maintain two evaluations: (a) chronological future activity for seen entities with strictly causal features, and (b) strict unseen-wallet/campaign/group holdout. Report both; do not present one as the other. Avoid giant public-service components consuming all splits: group adjudicated suspect/campaign links, document service-node exclusions and inspect cross-split leakage.

General time splitting alone does not enforce graph/group or label availability constraints. The independent splitter must implement all constraints. [Time-series split reference](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html).

### 13.2 M-12 — Training, tuning and imbalance

Train all parameters from fresh initialization. Record random seeds, deterministic options, hardware/software versions and data hashes. Use bounded random/Bayesian search over a preregistered search space on training/validation folds only, with early stopping where supported.

Handle class imbalance using training-only class/sample weights and/or documented within-fold sampling. Do not resample calibration/test prevalence. Any synthetic sampling must not connect unrelated graph entities or cross time/group boundaries. Report natural-prevalence metrics; correct calibration after altered training prevalence using an independent representative calibration set.

Threshold selection optimizes review workload and missed-risk cost on validation, not final test. Feature ablations must evaluate time, graph, protocol, correlation and data-quality dependencies. Unsupported chains/tasks remain experimental or unavailable.

### 13.3 M-13 — Calibration and confidence

Fit fresh sigmoid or isotonic calibration on data disjoint from classifier training/tuning as appropriate. Choose method using validation and adequate data; do not fit isotonic to a tiny calibration sample. Recalibrate the final ensemble, not merely its members. Calibration quality depends on deployment prevalence and cohort coverage. [Official probability-calibration reference](https://scikit-learn.org/stable/modules/calibration.html).

Required semantics:
- `positive_class_probability=p` in [0,1]: calibrated estimate of the explicitly defined supervised target.
- `risk_score=100*p` in [0,100], with documented rounding; not the composite-rule score.
- `predicted_class`: positive if p >= 0.5, negative otherwise, unless abstaining.
- `calibrated_confidence`: p for predicted positive, 1-p for predicted negative; also return p so confidence cannot be mistaken for risk.
- Operational review/high-risk threshold is separately configured and may differ from 0.5.
- Calibration status, calibrator version, applicable cohort and evaluated date accompany every result.

Do not manufacture confidence when the model is uncalibrated, out of scope or lacks required evidence. Return `abstained`/`unavailable` with null score/confidence and reasons, while retaining factual/rule findings. Statistical confidence intervals from evaluation must not be presented as certainty about an individual wallet.

### 13.4 M-14 — Evaluation metrics and proposed release targets

Targets below are proposed quality gates, not achieved results. Evaluate wallet and transfer tasks separately, on each enabled chain and temporal mode where supported. Preregister thresholds and bootstrap 95% intervals by wallet/campaign groups.

| Metric/gate | Initial required target |
|---|---|
| Data sufficient for a production claim | Final gold test per enabled task: >=200 adjudicated positives and >=200 negatives; each promoted chain cohort >=50 of each; otherwise research/shadow only |
| Precision at review threshold | Point estimate >=0.80 and 95% lower bound >=0.70 |
| Recall at review threshold | Point estimate >=0.60 |
| False-positive rate | <=0.05 on reviewed negatives at selected threshold |
| PR-AUC / average precision | Exceed prevalence baseline and independent logistic baseline; complex model selected only for measurable benefit |
| ROC-AUC | Report with interval; never the sole success measure |
| Calibration | ECE <=0.05 using preregistered ten equal-frequency bins plus reliability plot/counts |
| Probabilistic quality | Brier and log loss reported against prevalence baseline; calibration must not materially degrade either |
| Operating workload | Precision@K, recall@K, alerts per 1,000 observations and review volume at agency capacity |
| Selective prediction | Report coverage/abstention and metrics at each confidence/coverage level |
| Patterns/typology | Per-class precision/recall/F1 and macro-F1; under-supported labels abstain rather than inherit pooled success |
| Cohort safety | FPR gap <=0.05 for sufficiently sampled supported cohorts or documented restricted deployment/remediation |
| Robustness | Mandatory test suite; no silent valid-score output for missing/tampered evidence |

If gates conflict or lack sufficient data, do not relax them after seeing the final test. Keep shadow/research status, collect data, or approve a separately documented revised acceptance protocol before a new untouched test. Narrow deployment scope explicitly. Report prevalence, label uncertainty, censoring, sampling and confidence intervals.

### 13.5 M-15 — Reproducibility and experiment tracking

Use an independent experiment tracker (MLflow or equivalent service) and immutable artifacts. Record experiment/run ID, dataset and label snapshot hashes, source licenses, split membership/dates, feature/schema version, configuration/search space, candidate seeds, optimizer/parameters, all metrics/plots, package lock, hardware, model hash, calibrator hash, threshold/policy, reviewers and approval.

Retain failed runs and negative results. A fresh run from frozen inputs must reproduce predictions within declared numeric tolerance and evaluation metrics within 0.01 absolute where hardware nondeterminism exists; otherwise investigate and document. Exact artifact inference should reproduce within 1e-6 on the same runtime.

## 14. Deployment / Inference

### 14.1 M-16 — Serving package

Deploy a signed/hashed immutable package containing only new model(s), preprocessing, feature schema, calibrator, thresholds, explanation configuration, supported networks/tasks/modes, dependencies and model card. Validate schema/hash compatibility before readiness.

Inference requests name a case/wallet/transfer snapshot, report cutoff revision, event/knowledge cutoffs and purpose. Authorized service derives features from evidence; clients cannot submit arbitrary trusted feature vectors or choose unauthorized hidden data.

Pipeline: validate scope → pin snapshot/model → fetch eligible materialized features → quality/OOD gate → inference → calibration → policy → persist prediction and explanation references → return. No training, public provider traversal or model download on the synchronous path.

### 14.2 M-17 — Latency, availability and fallback

Interactive prediction target p95 <=1 second with materialized features under reference load; explanation may be asynchronous within 10 seconds. Missing feature materialization returns 202, not an inaccurate instant prediction.

VASP deposit-check p95 <200 ms is a separate end-to-end target for warm registry/prepared features. It includes authentication, lookup/eligible fast inference, policy and durable alert decision, excluding partner network where separately reported. New deep trace time must not be hidden inside this claim.

Fallback order: previous approved version of the NEW subsystem for the same scope, if compatible; otherwise explicit ML unavailable with independently defined deterministic findings. Never fall back to old backend ML. A stale/new-model-incompatible registry entry is not a current prediction.

### 14.3 M-18 — Promotion and rollback

States: `draft`, `training`, `validated`, `shadow`, `canary`, `production`, `retired`, `blocked`. Promotion requires quality, calibration, scope, privacy, adversarial, performance and independent-review gates.

Run shadow first, then a version-pinned canary without expanding automatic enforcement. Compare latency, errors, score distribution and matured outcomes. Record approvals and model traffic assignment.

Rollback atomically to the last approved compatible NEW model package/calibrator/feature schema/policy. Invalidate incompatible caches and leave prior prediction records intact. If no valid new version exists, abstain and retain rules/manual review. Retire old ML entry points only through documented API adapters; no runtime old code dependency is permitted.

## 15. Explainability / Human Review

### 15.1 M-19 — Explainable results

Every scored prediction shall provide score, calibrated confidence, model/calibrator/feature versions, temporal mode, report revision, cutoffs, evidence snapshot, top contributing signals, risk-reducing signals where supported, coverage/limitations and review state.

For each signal return feature name, measured value/unit, window, pre/post partition, baseline/reference, contribution, contribution space (log-odds/probability/score), direction, supporting transfer IDs, timestamps, paths and source references. Use fresh model-appropriate local explanations; for linear models coefficient-based contributions, for tree/ensemble candidates independently configured attribution methods. Validate faithfulness and perturbation stability.

Do not claim attribution values are causal or percentage points unless their output space supports that claim. No fabricated SHAP or substitute reason strings. If explanations fail, prediction metadata shows explanation_failed and no unsupported explanation is published.

“AI reasoning” means an auditable evidence rationale, not hidden model reasoning or an invented narrative. Generated text, if used, is local, constrained to verified fields and reviewed against source evidence.

### 15.2 M-20 — Review and override

Analysts may confirm, reject, mark uncertain, request more evidence, adjust operational priority, or override a recommendation with reason and evidence. Preserve original model output. Store before/after decision, actor, time, scope, reason, evidence, expiry and review version.

An override does not edit the model probability. Overrides expire or require review after material evidence/model/cutoff changes. Conflicting reviews route to adjudication. Automated enforcement is out of scope; VASP partners remain responsible for credit/hold decisions under their process.

Review feedback becomes a candidate label only after independent adjudication and label maturity checks. Monitor selection bias by sampling low-score/nonalerted records as well as high-score cases.

## 16. Monitoring / Drift / Retraining

### 16.1 M-21 — Monitoring

Track serving latency/errors, model/schema versions, abstention, missingness, provider/feature lag, input and prediction distributions, score/calibration cohorts, review disagreement/overrides and delayed outcomes. Separate baseline/post-report/retrospective modes, chains, tokens, protocol families, provider coverage and complaint sources.

Monitor PSI/KS or suitable distribution distances with minimum sample sizes and multiple-test handling; these are drift indicators, not proofs of performance degradation. Proposed triggers: PSI >0.20 on two consecutive daily windows with >=1,000 observations, missingness increase >10 percentage points, ECE >0.08 on >=200 matured labels, or observed review precision below 0.70 after adequate maturity. Calibrate operational thresholds on observed baseline distributions before promotion.

### 16.2 M-22 — Drift response and retraining

Investigate data quality/provider changes first. Distinguish covariate shift, prior/label shift, concept drift, delayed labels, graph-topology change, and adversarial change. Trigger a review when quality gates fail or a major chain/protocol shift occurs.

Monthly evaluation is required; retraining is conditional on sufficient new adjudicated data, drift or planned model improvement, not automatic publication. Freeze fresh data/labels; create time/group splits; retrain from new initialization; retune/calibrate; pass all gates; shadow/canary; obtain approval. Never train online directly from unreviewed complaints or overrides.

Record trigger, dataset additions, label delays, metric changes, promotion/rollback decision and affected cohorts. Preserve a previous approved NEW model for rollback.

### 16.3 M-23 — Fairness

Exclude protected victim/suspect identity attributes from scoring. Audit permissible cohort error/calibration differences by chain, asset, wallet activity, language of narrative, complaint source and coverage; use sensitive attributes only under separately approved fairness evaluation access.

Nationality, FIU status, use of a privacy tool or complaint geography alone shall not determine fraud labels. Evaluate legitimate mixer/bridge users and high-volume services. Report sample counts/intervals; small cohorts are “insufficient evidence,” not “fair.” Restrict scope or remediate when Section 13 gates fail. Record group-related harm analysis and reviewer escalation.

### 16.4 M-24 — Privacy/security and adversarial robustness

Protect training records/features/artifacts with scoped access, encryption, purpose limitation and audit. Pseudonymize identities; do not log narratives or secret credentials. Secure the registry against artifact replacement and use safe trusted loading. Test membership/data-extraction exposure where model access allows it.

Test poisoning through duplicate/sybil complaints, false exchange labels, manipulated source timestamps, dusting, benign high fan-out, threshold evasion, token-symbol spoofing, bridge/mixer lookalikes, missing providers and crafted narrative instructions. Deduplicate complaints, review label sources, validate contracts, retain provenance, rate-limit inference and quarantine anomalies.

Legitimate transfers should not become suspicious solely due to unsolicited dust. No robustness test shall be interpreted as guaranteed resistance to all attacks.

## 20. Security / Privacy / Auditability

Enforce agency/case/role/partner authorization on REST, graph filters, context, predictions, explanations, SSE/WebSocket, reports, search, totals and model administration. Admin visibility is policy-scoped. Read-only ML status exposes no weights or sensitive training examples.

Use secure password hashes, expiring JWT/session validation, refresh revocation, scoped partner keys and rate limits. Remove production default credentials. Restrict CORS to configured origins; TLS; secure refresh cookies where used with CSRF protection; avoid long-lived browser local-storage tokens in production.

Provider credentials use environment injection only, never source code, frontend variables, logs, query echoes or PRD sample secrets. Narratives/PII remain local/approved; model artifacts and features receive access controls. Privacy retention/legal holds apply to training snapshots too.

Validate imports, addresses, timestamps, graph limits and outbound allowlists. Use parameterized SQL/Cypher. Escape report content. Protect against SSRF, prompt injection, token spoofing, oversized payloads and model/label poisoning.

Audit submissions, report-time revisions, all graph filters/context access, inference requests/cutoffs, model promotions/rollback, label/review changes, overrides, case transitions, directory changes, sensitive reads/downloads and dispatch. Configurable operational countdown begins only on the documented event and is labeled accordingly.

## 21. Error Handling / Resilience

| Situation | Required behavior |
|---|---|
| Invalid wallet/network/time | 422 with field errors; no silent skip or guessed network |
| Missing report time/reference | 422 REPORT_TIMESTAMP_REQUIRED/REPORT_REFERENCE_REQUIRED for dependent post-report request |
| Cutoff revision incompatible with snapshot | 409 SNAPSHOT_CUTOFF_MISMATCH |
| Wrong cursor/filter/scope | 400 INVALID_CURSOR or forbidden response; no mixed-page results |
| Ineligible feature time | 422 TEMPORAL_SCOPE_VIOLATION; audit and fail closed for prediction |
| Model unsupported/missing/uncalibrated | Explicit abstention or 503 MODEL_UNAVAILABLE; never old ML fallback |
| Feature calculation pending | 202 with durable job status |
| Provider quota/outage | Retry-After, bounded retries/failover, partial/unavailable coverage |
| Registry outage | No safe/zero-risk default; unavailable or explicitly qualified manual review |
| Graph projection lag | State revision/lag; use authorized authoritative snapshot or partial response |
| Queue dispatch failure | Persisted outbox retries; accepted work remains recoverable |
| Report storage/hash failure | Failed generation/verification; no ready download |
| Invalid auth/access | 401/403, consistent object-level non-disclosure |
| Unhandled fault | 500 standard envelope, sanitized message and request ID |

Initial provider policy: connect3s/request10s, at most3 transient retries, exponential backoff+jitter, honor429/Retry-After and total run budget. No repeated retries for invalid credentials/address. Circuit breakers and per-provider/network quota coordination are required.

Cache keys include network/asset, case/access scope where needed, snapshot/revision, report-event revision, temporal view/boundary/context/to/filter, provider schema and model/calibrator/feature versions. A filter-only request must not accidentally reuse an all-history aggregate or another cutoff's prediction.

Historical finalized payloads may cache by block/hash; old address pages up to6h; active wallet history15–30s; pending5–15s; directory15m with immediate invalidation; aggregates15s. Feature/prediction caches are immutable snapshot/version keyed. Registry age/expiry is explicit; risk retention is not freshness.

Use separate eviction-safe broker/registry storage and disposable cache policies. Persist checkpoints, detect worker lease expiry, requeue idempotently and support bounded cancellation. Finality/reorg corrections revise active conclusions and alert affected users while retaining historical evidence.

Logs/metrics include request/run/model versions, durations, queue age, provider lag/quota/failures, cache stale/hits, graph lag, prediction/abstention/explanation failures, drift and document integrity. Exclude PII/secrets.
